# Agent Note: 接管持有者已退出的写锁

Status: implemented

[English](2026-09-24-exited-holder-lock-takeover.md) | 中文

## 问题

[dsh-atomic-write](../../../../packages/util/atomic-write/README.zh.md) 的 `withFileLock` 以独占创建方式创建 `<file>.lock`，并在 `finally` 中移除它。进程若未执行该 `finally` 就结束，锁会留在原地，该文件后续的每个写入方都会超时，直到有人手动删除它。[原始决策](../../archived/architecture/2026-07-30-settings-write-path-integrity.md)接受了这一点，因为文件存续时间无法区分已崩溃的持有者与暂停的持有者。

profile 包锁（`<profile>/package.json.lock`）让这个代价显现出来。`dsh plugin` 不安装信号处理器，因此在 pnpm 运行期间按 Ctrl-C、发送 SIGTERM 或关闭其终端都会结束进程，锁随之留下。`dsh` 与 `dsh web` 在应用销毁完成后立即退出，而此时被取消的安装仍在恢复文件，尚未释放锁。崩溃、SIGKILL 或内存不足被杀也有同样效果。发生上述任一情况后，该 profile 上的每个插件操作都会在 `lockWaitMs`（默认两分钟）后失败，且不说明持有者已不存在。

## 决策

- 锁记录 `{ pid, hostname, nonce }`。随机数让每条记录唯一，因此之后的锁不会重复已退出持有者的记录。
- 竞争者发现锁时读取其记录。若记录指向本机，且对该 PID 的信号探测以 `ESRCH` 失败，则证明持有者已不存在，锁会被接管。`EPERM` 表示该进程以其他用户身份存在，锁保留。
- 读到同一条记录的竞争者通过一个以 `wx` 创建的认领文件 `<file>.lock.takeover-<记录 SHA-256 的前 16 位十六进制>` 串行化。认领者重新读取锁，仅当锁仍是该记录时才移除它，随后移除认领文件并立即重试获取。记录只能经由另一次接管改变，而那需要同一个认领文件，因此认领者绝不会移除另一个竞争者在已退出持有者之后获得的锁。
- 记录为空、无法解析、缺少主机名、指向其他主机或 PID 小于等于零时，竞争者继续等待。这些情况都无法证明持有者已经停止。
- 早期版本写入的仅含 PID 的记录视为在本机写入，因此本变更之前遗留的锁也会被接管。

## 考虑过的替代方案

**移除超过固定时长的锁。** 时长无法区分已崩溃的持有者与正在运行十分钟 pnpm 安装的持有者，而插件管理器会合理地持锁这么久。

**由内核释放的锁（`flock`、`LockFileEx`）。** 持有者死亡时内核会释放它们，从根源上消除问题而不是检测它。原生 `flock` 入口仅支持 POSIX，Windows 绑定尚不存在，且每个 `withFileLock` 调用方都会依赖原生插件。若 PID 复用或其他主机记录变得重要，这仍是更强的修复。

**把陈旧锁重命名到别处，若重命名后的记录不同再恢复。** 恢复可能与在此间隙获取空路径的第三个竞争者竞态，导致出现两个持有者。认领文件无需任何恢复即可防止这一竞态。

**只在 `dsh plugin` 中安装信号处理器。** 这只覆盖留下锁的其中一条路径，崩溃、强制退出和其他锁文件仍会遗留。

## 验证

| 证据 | 行为 |
|---|---|
| [atomic-write.spec.ts](../../../../packages/util/atomic-write/tests/atomic-write.spec.ts) | 接管已退出持有者的当前格式记录与仅含 PID 的记录；八个竞争者同时接管一个已退出持有者时从不重叠；存活、其他用户、其他主机、空、无法解析、缺少主机名和进程组记录均继续等待；无法读取的锁、被另一竞争者持有的认领、认领后被替换的记录都保留原样；Windows 对认领的拒绝会重试，其他认领失败会抛出，认领无法移除时操作不失败。 |

## 后果

- 同一主机上已退出进程留下的锁不再需要操作者处理；下一个写入方无需等到期限即可继续。
- 重启后被存活进程复用的 PID 会让锁保持原样，直到操作者移除，与之前相同。
- 持有者退出与下一个写入方之间主机名发生变化（macOS 切换网络时会这样）会让锁保持原样。
- 共享主机名但不共享 PID 命名空间的进程，例如在同一卷上使用宿主 UTS 命名空间启动的容器，可能把存活持有者视为已退出。不支持此类部署。
- 竞争者在持有认领文件时崩溃会留下该认领文件，对应的锁随后不会被自动接管。
- 仍存活的持有者会保留其锁，因此本变更不限制存活操作的持锁时长。
